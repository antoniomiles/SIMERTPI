# CP25.2-B — Autenticación backend municipal

## Contrato añadido

- `POST /api/v1/municipal/auth/login`: username/password; solo emite sesión a una cuenta habilitada con `INSPECTOR`.
- `POST /api/v1/municipal/auth/refresh`: renueva y rota la sesión de audiencia municipal.
- `POST /api/v1/municipal/auth/logout`: revoca la sesión municipal; repetir el logout de la misma sesión no falla.
- `GET /api/v1/municipal/auth/me`: devuelve `userId`, `username`, roles actuales y estado habilitado sin datos de contraseña ni hashes.

Las respuestas de sesión y perfil utilizan `Cache-Control: no-store`. Los errores de credenciales, sesión inválida o cuenta deshabilitada son genéricos. Una contraseña válida sin autoridad `INSPECTOR` recibe 403 en el login municipal.

## Aislamiento y sesiones

V41 añade `identity.mobile_sessions.audience`, con default y backfill `CITIZEN` para preservar todas las sesiones previas. Los dos clientes continúan usando las tablas existentes de sesiones y refresh tokens; los tokens siguen siendo aleatorios y almacenados solo como SHA-256. Login, validación, refresh y logout exigen el ámbito esperado. Los endpoints municipales de inspección, infracciones, evidencias y advertencias verbales aceptan únicamente Bearer municipal. Un Bearer municipal no se admite en rutas ciudadanas; un Bearer ciudadano no se admite en rutas municipales. HTTP Basic existente no se cambia.

Los TTL municipales son configurables con `simertpi.municipal-auth.access-ttl` (15m por defecto) y `simertpi.municipal-auth.refresh-ttl` (30d por defecto). La renovación vuelve a comprobar cuenta habilitada y rol. Si la cuenta se deshabilita o pierde `INSPECTOR`, la siguiente autenticación o renovación rechaza y revoca la sesión.

## Aprovisionamiento

El registro público actual crea únicamente usuarios `CITIZEN`; no existe endpoint de asignación o baja de roles municipales. El rol `INSPECTOR` se siembra como catálogo, pero el repositorio no ofrece una API operativa para concederlo ni una rutina de baja municipal. Por tanto, todavía no hay un procedimiento de aprovisionamiento ejecutable y aprobado para el piloto. Antes de habilitar inspectores debe aprobarse un runbook administrativo con verificación de identidad, autorización/segregación de funciones, registro de auditoría, alta y baja, y entrega inicial de credencial por canal seguro. No usar cuentas o contraseñas predeterminadas, no habilitar el alta desde la app móvil y no asignar roles mediante operaciones improvisadas.

## Compatibilidad futura con biometría

El esquema de sesión tiene ámbito explícito y conserva el campo de método de autenticación. Una futura credencial pública debe quedar ligada a usuario, dispositivo y audiencia municipal; el backend deberá verificar desafíos firmados y emitir sesiones `MUNICIPAL` tras volver a validar habilitación y rol. CP25.2-B no añade claves, desafíos ni endpoints biométricos.

## Alcance

Esta entrega no incluye Flutter, turnos, administración de usuarios ni despliegue. V41 se ejecuta únicamente en bases locales de prueba por Flyway; no se aplicó en Render.
