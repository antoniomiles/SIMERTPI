# CP25.2-C — Login Flutter municipal

## Contratos usados

El cliente usa exclusivamente los contratos de CP25.2-B bajo `/api/v1/municipal/auth`:

- `POST /login`: envía `username` y `password`; recibe `userId`, `tokenType`, `accessToken`, `refreshToken`, `accessExpiresAt` y `refreshExpiresAt`.
- `GET /me`: consulta la identidad vigente y requiere `Authorization: Bearer <accessToken>`; devuelve `userId`, `username`, `roles` y `enabled`.
- `POST /refresh`: envía `refreshToken` y recibe el nuevo par rotado.
- `POST /logout`: envía el `refreshToken` y espera `204`.

El cliente no confía en roles del formulario ni en roles guardados localmente. Después de login y refresh exige que `/me` confirme usuario habilitado con `INSPECTOR`; solo entonces muestra el inicio protegido.

## Sesión y fallos

Los tokens y sus fechas de expiración se almacenan como un único registro en `flutter_secure_storage`. La contraseña vive solo durante la solicitud de login. Al iniciar la app se valida `/me`; si el access token venció, se rota el refresh y se vuelve a validar el perfil. La renovación se programa antes de expirar y se reevalúa al volver a primer plano. Solicitudes simultáneas de refresh comparten una misma operación. Logout intenta revocar en backend y borra el registro local incluso si el servicio no responde.

401, 403, conectividad, timeout, formato de respuesta y error de almacenamiento tienen clasificaciones seguras para la interfaz. No se registran cuerpos de autenticación ni tokens.

## Configuración

`SIMERTPI_API_BASE_URL` debe terminar en `/api/v1`. Se exige HTTPS, excepto HTTP loopback en development. No hay URL de producción incorporada y los Dart defines no contienen secretos.

El backend CP25.2-B y V41 aún deben estar disponibles en el entorno para probar el login real. No se aplicó Flyway ni se hicieron llamadas a Render/DEV desde esta implementación.

CP25.2-C no incluye biometría, turnos ni pantallas operativas.
